# 项目历史吸收

仅在当前用户明确选择时使用。安装、升级、PreInvocation、Stop、空知识库和普通“继续”均不启动或恢复历史吸收。

- v1.1.4：先检查 `history-prepare --confirm` 的 `preparation.action`。`continue_existing` 表示前批主审未结束，未重新扫描；`no_changes` 表示未发现新增内容。不要因重复点击直接再次运行或创建批次，先报告现有进度，按当前明确授权续审；预算暂停、未知调用、旧账户与用户主动暂停仍核对原状态。
- 主审、补证和批准分开统计；待补证与待批准不阻挡新的增量。需切换范围时，由用户明确选择后用 `history-defer <job_id> --reason <原因> --confirm` 暂存旧主审，保留记录和访问边界。随后 `history-prepare --mode incremental --confirm` 只排入新增或变化来源；`--mode remaining` 优先补扫原选择中因文件数、字节数或分段预算遗漏的文件，沿用原上限，不用于未知格式或目录枚举上限；`--mode full` 仅用于用户明确要求的全量。新扫描不会自动启动模型。

- 核对固定工作区、数据目录和对应运行副本。多工作区无法确定归属时先让用户选择。`transcriptPath` 和 `artifactDirectoryPath` 只是来源提示；不自动读取它们或扩大到上级历史目录。
- 使用本地显式 CLI，所有 `history-*` 命令传 `--workspace` 和 `--host antigravity`，保持固定 `--home`。普通及管理员 MCP 没有启动／批准入口；`--confirm` 不构成人类身份认证。
- 用户明确选定项目和额外来源后，使用 `history-prepare --confirm`；`--conversation-file` 和 `--artifact-dir` 仅指向选定资料。程序完整读取支持文本，保存脱敏版本与覆盖清单，不执行项目代码、不保存内部思考。
- 用户已经批准本次归档时，使用 `history-run <job_id> --confirm`。仅在另外明确允许模型整理时增加 `--allow-review`，同时限定调用和时长；按受信策略使用对应宿主 CLI。current 模式仅在当前项目／宿主具有唯一有效根模型时可整理历史，否则保留待处理，由用户明确选择 fixed 或 default。不开启日常管理员，不自动发布。
- `main` 的增强整理优先安排项目说明、Agent 总结、备忘等文档，在已批准且已归档的资料中加入有限相关参考。单次历史模型调用最多五条候选，不要求凑数；旧 v1.0.0 包不含此增强。相关参考不算完成了该来源的主审核，多条候选也不能计为多次审核。
- 人工管理员先用 `history-cases <job_id>` 定位当前批次的准确案例 ID，再用现有 `packet`／管理员 MCP 整理。陈述保持 `reported`；候选经独立入口发布，历史流程不自动发布。
- 用 `history-status` 分别报告已归档来源、实际主审核、待补证／未触及单元、候选和正式发布；归档完整不表示全项目已理解。未解析、超限和冲突需报告；暂停、取消、预算不足或换号后不自动续做。显式续跑仍用 `history-run --confirm` 并限定调用及时长，依据保存回执复用有效审核。
- 用户要审批候选时调用 `learning-review` 打开同一项目、同一数据目录的可视化审批台，由用户查看证据并选择批准发布、拒绝或暂缓；打开页面和候选生成不代表发布授权。
- 更新提示若通过 `ephemeralMessage` 提供，应向用户转述新版说明和选择；它不是用户消息或安装授权。用户明确选择后再设置 `update-choice` 或执行授权更新。更新不启动历史吸收。

完整命令与边界见 [项目说明](../../README.md)。
